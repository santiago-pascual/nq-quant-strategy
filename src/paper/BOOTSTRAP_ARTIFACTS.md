# Causal Paper bootstrap artifacts

Future deterministic and OOS Paper runs write `bootstrap_progress.json` in
their own run directory. This is an atomic, replace-on-write status snapshot;
it is separate from `paper_checkpoint.json`, the analytics database, and the
event ledger. It reports the current preparation stage, stage/run elapsed time,
historical row counts, last completed UTC timestamp, and any active MR/S2R
refit. Updates are throttled by elapsed time and row count, with forced writes
at stage changes and refit boundaries. A long vectorized pandas operation may
remain on the same stage until that operation returns; the progress file does
not claim incremental work inside a single vectorized call.

Stages include canonical data loading, data-boundary validation, session-final
bar marking, historical warm-up selection, feature-cache identity/lookup,
individual feature families, causal HMM bootstrap, and Paper service startup.
The dashboard may read this small file; it must not scan intermediate feature
frames or query a bootstrap database.

## Feature cache

The runner uses `data/cache/paper_causal_features/`, configurable with
`--feature-cache-dir`. The cache stores Parquet features plus a JSON manifest.
The key includes an ordered OHLCV/timestamp/market-period data fingerprint and
any available Databento identity columns (`symbol`, `instrument_id`,
`contract_id`, `dataset`, `schema`),
the source of the feature builder and its helper functions, the feature schema
and warm-up contract, timezone, and Python/pandas/NumPy versions. Cache writes
use a temporary file and atomic rename. Reads check key/manifest identity,
file SHA-256, row count, column uniqueness, dtypes, and timestamp coverage.
Missing, partial, corrupt, or incompatible entries are rejected and rebuilt.
If persistence fails after a successful in-memory build, the current run uses
that just-built frame and records the cache write failure. Cache data is
recomputable and is not a trading checkpoint.

Only the already-selected historical `history` frame (strictly before the
strategy start) is passed to the cache or feature builder. It never receives
the OOS stream. Feature formulas, rolling windows, RTH/ETH rules, HMM math,
raw component IDs, refit schedules, strategies, and risk rules are unchanged.
The cache is an optimization; numerical parity must be checked before relying
on a cache generated by a new runtime.

## Full causal bootstrap CLI

The orchestration entry point is `python -m src.paper.causal_bootstrap_cli`.
It reuses `CausalBootstrapRunner`; it is not a second feature/HMM engine.

```powershell
$env:OMP_NUM_THREADS='1'
$env:OPENBLAS_NUM_THREADS='1'
$env:MKL_NUM_THREADS='1'
$env:LOKY_MAX_CPU_COUNT='4'
python -m src.paper.causal_bootstrap_cli validate
python -m src.paper.causal_bootstrap_cli benchmark `
  --benchmark-start 2024-07-05T00:00:00Z `
  --benchmark-end 2026-10-08T13:03:00Z `
  --split-rows 1000000 `
  --output results/diagnostics/causal_bootstrap_benchmark.json
python -m src.paper.causal_bootstrap_cli status `
  --checkpoint results/paper/causal_activation_seed.json
```

`benchmark` is bounded and never creates an activation artifact. `start` and
`resume` require `--confirm-full-bootstrap`, verify that the certificate
matches every raw partition, then run only if the certificate explicitly
attests complete activation coverage. The full-run commands, when coverage is
certified and an activation time has been selected, are:

```powershell
python -m src.paper.causal_bootstrap_cli start `
  --activation-utc <UTC_TIMESTAMP> `
  --certificate <REVIEWED_FULL_COVERAGE_CERTIFICATE.json> `
  --confirm-full-bootstrap
python -m src.paper.causal_bootstrap_cli resume `
  --activation-utc <UTC_TIMESTAMP> `
  --certificate <SAME_REVIEWED_CERTIFICATE.json> `
  --confirm-full-bootstrap
```

An uncertain absence in sparse trade-bar OHLCV is classified separately from
a demonstrated missing required observation: OHLCV alone cannot tell a
no-trade minute from capture loss. This uncertainty may be reported while
computing causal state over observed rows, but it is not promoted to a verified
calendar session and cannot authorize Paper activation. No bars are synthesized.

The activation seed contains context/HMM state, source/configuration and
coverage identities, a fresh account/risk seed, a checksum-protected
checkpoint, and an explicit constructor-default state seed for MRL1, MRS2,
S2R, and ORB. Historical trades, orders, positions, fills, and PnL are never
replayed into the fresh account.

## Causal HMM bootstrap resumption

`CausalBootstrapRunner` resumes at its last atomically committed row chunk.
The `CausalMarketContext.state_dict()` contains the state required by that
runner:
bounded rolling bars/features and RTH closes, volatility rank history, both
HMM streams, model/scaler parameters, forward posterior, fit timestamps,
training observations, refit schedule, and model diagnostics. The scheduled
MR stream retains expanding training history; S2R retains its rolling window.
The version-2 checkpoint is separate from Paper execution state and includes
source/configuration/runtime fingerprints, cache key, activation/origin,
coverage certificate digest, last committed row/timestamp, account seed,
strategy constructor-state seed, and context/HMM state. It is checksummed and
published by atomic replace. Resume rejects identity, schema, checksum, and
cursor mismatches. The current JSON payload can be large; compact binary
serialization and append-only chunk caches remain future performance work.

Fixture tests prove chunked checkpoint/resume equivalence. Real-data benchmark
results are recorded separately; a passing fixture does not certify full
history runtime, calendar coverage, or delayed-Paper activation.
